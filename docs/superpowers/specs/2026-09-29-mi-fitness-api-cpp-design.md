# Дизайн: mi-fitness-api, порт моста Mi Fitness на C++

Дата: 2026-09-29. Статус: на утверждении.

## Зачем

Сейчас данные Mi Fitness в кластер тянет [mi_fitness_data_bridge](https://github.com/shkyyy18/mi_fitness_data_bridge) на Python: SQLite на PVC плюс MCP-сервер за HTTP-прокси. Задача владельца: заменить это своим сервисом на C++ поверх `cpp-rapid-rest-template`, с REST API вместо MCP, данными в Postgres и токеном в Secret.

Успех выглядит так: сервис сам логинится в облако Xiaomi, тянет восемь типов записей, кладёт их в Postgres и отдаёт по REST с теми же числами, что отдаёт сегодняшний Python-мост на тех же датах. После этого Python-мост, его PVC и `mcp-proxy` удаляются из кластера.

## Решения, принятые до дизайна

1. Порт целиком, вместе с адаптером к Xiaomi. Сервис не зависит от Python ни в какой момент.
2. Один аккаунт Xiaomi, один потребитель API. Ни регистрации, ни ролей, ни почты, ни биллинга. Шаблон разворачивается через `./scripts/init-project.sh --minimal`.
3. Лицензия AGPL-3.0-only. Порт делается с чтением AGPL-кода, перевод на другой язык это производное произведение. MIT шаблона в AGPL-проект включать можно, обратно нельзя.
4. Топология: один образ, два деплоймента. REST в основном бинаре, синк в воркере через `Jobs` (Redis-очередь шаблона с ретраями и DLQ). Расписание ставит `Tasks::` таймер в API-процессе.
5. PVC нет ни одного. Состояние живёт в Postgres, секреты в Secret, очередь в Redis.
6. Первый этап сразу покрывает все восемь типов данных, а не один вертикальный срез.

## Ограничение, которое формирует половину дизайна

`passToken` ротируется при каждом логине: Xiaomi возвращает новый в ответе `serviceLogin`, и старый со временем перестаёт работать. Наблюдение от 2026-09-29: предыдущий токен оставался валиден минимум десятки минут после ротации, то есть инвалидация не мгновенная, но полагаться на это нельзя.

Отсюда схема хранения в две ступени:

1. Secret держит `MI_FITNESS_USER_ID`, стартовый `MI_FITNESS_PASS_TOKEN` и ключ `MI_FITNESS_TOKEN_KEY` (32 байта, base64) для шифрования.
2. Таблица `xiaomi_credentials` держит текущий живой токен, зашифрованный `crypto_secretbox_easy` из libsodium. Ключ в базу не попадает.
3. На старте сервис берёт токен из базы. Если строки нет, сеет её из Secret. Если задан `MI_FITNESS_RESEED=1`, перезаписывает базу значением из Secret.

Плюсом идёт то, что libsodium в шаблоне уже подключён и используется в `src/security/Password.hpp`, а поду не нужны права на запись в секреты кластера.

## Архитектура

Границы модулей так, чтобы каждый читался и тестировался отдельно.

```
src/xiaomi/
  Crypto.hpp/.cpp        RC4, nonce, signed_nonce, подпись. Чистые функции, без сети.
  CloudClient.hpp/.cpp   логин, ротация токена, подписанный POST, пагинация. Знает HTTP, не знает про домен.
  Normalize.hpp/.cpp     сырой JSON → доменные структуры. Чистые функции, без сети и без базы.
  Regions.hpp            таблица регион → хост, список кандидатов.
src/domain/
  Activity.hpp Sleep.hpp Workout.hpp Body.hpp Samples.hpp
src/repositories/
  ActivityRepository ... по одному на тип, плюс SyncStateRepository, CredentialsRepository
src/sync/
  SyncService.hpp/.cpp   нарезка диапазона, порядок типов, идемпотентная запись, учёт прогресса
src/jobs/
  XiaomiSyncHandler      обработчик задания в воркере, поверх Jobs шаблона
src/api/
  ActivityController SleepController WorkoutController BodyController SamplesController SyncController
```

Правило зависимостей: `Crypto` не знает ничего, `CloudClient` зависит только от `Crypto` и `Regions`, `Normalize` зависит только от домена, `SyncService` склеивает `CloudClient`, `Normalize` и репозитории, контроллеры зависят только от репозиториев. Контроллер никогда не дергает Xiaomi напрямую.

## Протокол, который надо перенести точно

Логин, две ступени:

1. `GET https://account.xiaomi.com/pass/serviceLogin?_json=true&sid=miothealth` с заголовком `Cookie: userId=<id>; passToken=<token>`. Ответ начинается префиксом `&&&START&&&`, дальше JSON. Обязательные поля: `passToken`, `userId`, `ssecurity`, `location`.
2. `GET <location>`, и в ответе обязана быть кука `serviceToken`. Редирект принимается только на хосты `xiaomi.com` и `mi.com` и их поддомены.

Новый `passToken` из ответа сохраняется до того, как пойдёт второй запрос: иначе сетевая ошибка на редиректе потеряет уже выданный токен.

Подписанный запрос данных:

1. `form = {"data": <компактный JSON payload>}`.
2. `nonce` = 8 случайных байт плюс 4 байта big-endian с номером текущей минуты от эпохи.
3. `signed_nonce` = `SHA256(ssecurity_bytes || nonce)`.
4. `rc4_hash__` = подпись от неизменённого form.
5. Каждое значение form шифруется RC4 и кодируется base64, затем считается `signature` уже от зашифрованных значений.
6. Подпись: `base64(SHA1("POST&" + path + "&data=" + data + ["&rc4_hash__=" + hash] + "&" + base64(signed_nonce)))`.
7. Тело уходит как `application/x-www-form-urlencoded`, ответ приходит base64 и расшифровывается тем же RC4-ключом.

RC4 здесь нестандартный: после инициализации ключевого расписания отбрасывается 1024 байта потока. Это обязательная деталь, без неё расшифровка даст мусор.

Эндпоинты и регионы:

| Что | Путь | Примечание |
| --- | --- | --- |
| Записи по времени | `/app/v1/data/get_fitness_data_by_time` | основной, пагинация по `next_key` и `has_more` |
| Суточные отчёты | `/app/v1/data/get_aggregated_fitness_data_by_time` | только для оценки сна |
| Тренировки | `/app/v1/data/get_sport_records_by_time` | отдельная форма записи |

Хост: `https://hlth.io.mi.com` для региона `cn` и пустого значения, иначе `https://<region>.hlth.io.mi.com`. Кандидаты регионов: `ru, cn, de, i2, sg, us`. Автоподбор региона перебирает кандидатов по ключам `weight`, `steps`, `heart_rate` и берёт первый, который ответил непусто.

Ключи типов данных в запросе: `steps`, `calories`, `sleep`, `weight`, `heart_rate`, `resting_heart_rate`, `spo2`, `stress`, `abnormal_heart_beat`.

Границы диапазона считаются в часовом поясе региона: для `cn` это жёстко UTC+8, для остальных UTC. Пагинация защищается потолком страниц и множеством уже виденных курсоров, чтобы петля курсора не превратилась в бесконечный цикл.

## Правила нормализации, которые нельзя упростить

Это не стиль, это корректность данных. Каждое правило получает свой тест.

1. Шаги агрегируются по паре (локальная дата, локальная минута). При нескольких записях за одну минуту от разных устройств берётся одна запись с наибольшим кортежем (шаги, дистанция, калории), а не сумма. Суммирование даёт завышение в дни с двумя устройствами. Подавленное количество шагов считается и логируется.
2. Ноль от сервера означает «нет данных», а не измеренный ноль. Такие значения уходят в базу как NULL.
3. Оценка сна берётся с самой записи. Если её нет, разрешено подтянуть оценку из суточного агрегата, но только на одну однозначно определённую главную сессию. Главной считается сессия с `is_nap = false`, длительностью больше нуля и не больше 1440 минут. При нескольких кандидатах отбор идёт по одному источнику и максимальной длительности, и если однозначности нет, оценка не ставится вообще. Никаких локальных вычислений оценки.
4. У оценки хранится происхождение: `sleep_record` или `daily_report`. Неизвестное происхождение это NULL.
5. Провал необязательного запроса суточных отчётов не выбрасывает сами сессии сна и не стирает ранее известную оценку при тех же границах и том же признаке дневного сна.
6. Пульс в покое кладётся в ту же таблицу, но с иным `sample_type`, поэтому ключ уникальности включает его.
7. Повторный синк того же диапазона идемпотентен: записи не дублируются.

## Схема Postgres

Восемь таблиц данных повторяют состав SQLite, но с типами Postgres и естественными ключами вместо строкового `id`. Общая часть у всех: `provider text`, `source_type text`, `source_record_id text`, `user_id text`, `device_id text`, `timezone text`, `collected_at timestamptz`, `created_at timestamptz default now()`, `updated_at timestamptz`.

| Таблица | Специфичные колонки | Ключ уникальности |
| --- | --- | --- |
| `daily_activity` | `date date`, `steps int`, `distance_m double precision`, `active_kcal double precision`, `total_kcal double precision`, `floors int`, `active_minutes int` | `(user_id, date, device_id)` |
| `sleep_sessions` | `sleep_id text`, `start_at timestamptz`, `end_at timestamptz`, `duration_minutes int`, `time_asleep_minutes int`, `time_awake_minutes int`, `sleep_score int`, `sleep_score_source text`, `is_nap boolean`, `stages jsonb` | `(user_id, sleep_id)` |
| `workouts` | `workout_id text`, `activity_type text`, `start_at`, `end_at`, `duration_minutes int`, `distance_m`, `calories_kcal`, `avg_heart_rate_bpm int`, `max_heart_rate_bpm int`, `avg_pace_sec_per_km`, `max_pace_sec_per_km`, `total_steps int` | `(user_id, workout_id)` |
| `body_measurements` | `timestamp timestamptz`, `weight_kg`, `bmi`, `body_fat_pct`, `muscle_mass_kg`, `water_pct`, `bone_mass_kg`, `visceral_fat_score int`, `basal_metabolism_kcal int`, `metabolic_age int` | `(user_id, timestamp, device_id)` |
| `heart_rate_samples` | `timestamp timestamptz`, `bpm int`, `sample_type text` | `(user_id, timestamp, sample_type)` |
| `spo2_samples` | `timestamp timestamptz`, `spo2_pct int` | `(user_id, timestamp)` |
| `stress_samples` | `timestamp timestamptz`, `stress_score int`, `level text` | `(user_id, timestamp)` |
| `abnormal_heart_beat_events` | `event_id text`, `start_at`, `end_at`, `duration_seconds int` | `(user_id, event_id)` |

Три служебные таблицы:

1. `xiaomi_credentials`: `user_id text primary key`, `pass_token_sealed bytea`, `nonce bytea`, `region text`, `rotated_at timestamptz`.
2. `sync_state`: `data_type text primary key`, `last_sync_at timestamptz`, `last_record_timestamp timestamptz`, `records_count bigint`.
3. `sync_runs`: `id bigserial`, `started_at`, `finished_at`, `status text` (`running`, `succeeded`, `failed`, `interrupted`), `requested_start date`, `requested_end date`, `data_types text[]`, `result jsonb` с количеством добавленных, обновлённых и пропущенных записей по типам.

Запись идёт через `INSERT ... ON CONFLICT (ключ) DO UPDATE`, что и даёт идемпотентность вместо ручной проверки существования. Миграции создаются генератором шаблона `make new-migration`.

## REST API

Префикс `/api/v1`, авторизация по API-ключу шаблона, ответы в конверте шаблона, каждый маршрут обязан быть одновременно в контроллере, в `Api::get_endpoints()` и в `docs/openapi.yaml`, иначе CI не пройдёт.

| Метод и путь | Параметры | Отдаёт |
| --- | --- | --- |
| `GET /api/v1/activity` | `from`, `to`, `limit`, `offset` | суточная активность |
| `GET /api/v1/sleep` | `from`, `to`, `include_naps`, пагинация | сессии сна со стадиями |
| `GET /api/v1/sleep/summary` | `from`, `to` | средние по локальной дате пробуждения, доля сессий с оценкой |
| `GET /api/v1/workouts` | `from`, `to`, `type`, пагинация | тренировки |
| `GET /api/v1/body` | `from`, `to`, `metrics`, пагинация | вес и состав тела |
| `GET /api/v1/samples/{kind}` | `kind` ∈ `heart_rate, spo2, stress, abnormal_heart_beat`, `from`, `to`, пагинация | точечные замеры |
| `GET /api/v1/coverage` | нет | по каждому типу первая и последняя дата, число дней, время последнего синка |
| `POST /api/v1/sync` | тело с `from`, `to`, `data_types` | ставит задание в очередь, возвращает `run_id` |
| `GET /api/v1/sync/{run_id}` | нет | статус запуска и счётчики по типам |
| `GET /api/v1/export` | `format` ∈ `json, csv`, фильтры как у остальных | выгрузка, совместимая по смыслу с `schema_version 1.0` Python-моста |

Даты во входе строго `YYYY-MM-DD`, `from` не позже `to`, фильтры включают границы. Пагинация как в шаблоне: `limit`, `offset`, признак следующей страницы.

Числовые поля, которых в данных нет, отдаются как `null`, а не как ноль. Это продолжение правила 2 из нормализации и часть контракта API.

## Синхронизация

1. `POST /api/v1/sync` создаёт строку в `sync_runs` и ставит задание типа `xiaomi_sync` в очередь `Jobs`. Отвечает сразу, тело с `run_id`.
2. `Tasks::` таймер в API-процессе раз в сутки ставит то же задание с окном последних `MI_FITNESS_LOOKBACK_DAYS` дней, по умолчанию четыре. Окно шире одного дня потому, что Xiaomi доливает историю задним числом: 28 сентября 2026 в один и тот же день сначала показывало 100 шагов, после пересинка 2303.
3. Воркер берёт задание и идёт по типам последовательно, каждый тип нарезая диапазон по `MI_FITNESS_CHUNK_DAYS` дней, по умолчанию семь.
4. У каждого типа свой потолок времени, `MI_FITNESS_SYNC_TYPE_TIMEOUT`, по умолчанию 180 секунд. На диапазоне в четыре месяца этого мало, поэтому для догрузки истории значение поднимается через переменную. Потолок именно на тип, а не на весь запуск.
5. Одновременно работает один синк. Гарантия даётся консультативной блокировкой Postgres `pg_try_advisory_lock`, а не только настройкой очереди. Не получил блокировку, задание завершается со статусом `skipped`.
6. Провал одного типа не отменяет остальные. Результат по каждому типу пишется в `sync_runs.result`, а неудачное задание уходит в DLQ шаблона.
7. Незавершённые при перезапуске запуски помечаются `interrupted` и не подхватываются автоматически.

## Ошибки

1. Ошибка авторизации Xiaomi отличается от сетевой: первая не ретраится очередью, а пишет в `sync_runs` статус `failed` с признаком `auth` и поднимает метрику. Ретрай тут только сожжёт попытки.
2. Тексты ошибок от сервера, значения токенов и идентификаторы аккаунта не попадают ни в логи, ни в ответы API. Маскирование как в Python-мосте: шесть звёзд и два последних символа.
3. Пустой успешный ответ это не ошибка. Ноль записей означает, что записей такого типа в диапазоне нет.
4. Ошибка расшифровки или подписи трактуется как несовместимость протокола: отдельная метрика, потому что это первый признак того, что Xiaomi поменял формат.

## Тесты

Ключевая проблема порта: у Python-моста 297 тестов, у нового кода их нет, а проверять числа на живом аккаунте медленно и невоспроизводимо. Поэтому:

1. Золотые векторы для крипты. Одноразовым скриптом на Python снимаются пары вход-выход для RC4 с отбросом 1024 байт, `signed_nonce` и подписи на фиксированных входах, и кладутся в `tests/fixtures/xiaomi_crypto_vectors.json`. Тест на C++ гоняет их же. Это ловит все ошибки переноса алгоритма без сети и без аккаунта.
2. Нормализация проверяется на синтетических ответах, снятых с формата Python-фикстур. Обязательные случаи: две записи в одну минуту от разных устройств, ноль как отсутствие данных, сон через полночь, дневной сон рядом с главной сессией, неоднозначные кандидаты на оценку, повторный синк того же диапазона.
3. Клиент проверяется против локального мок-сервера: префикс `&&&START&&&`, отсутствие обязательных полей, редирект на посторонний хост, отсутствие `serviceToken`, петля курсора, ротация токена посреди сессии.
4. Репозитории и API проверяются интеграционными тестами шаблона на живом Postgres, e2e-бакет сверяет ответы со схемами `docs/openapi.yaml`.
5. Приёмка на настоящих данных: за одну и ту же неделю выгрузка из Python-моста и из нового API должны совпасть по шагам, дистанции, весу и границам сессий сна. Это единственная проверка, которая ловит ошибки понимания протокола, и она обязательна до удаления Python-моста.

## Чего в этом проекте нет

1. MCP в любом виде.
2. Многопользовательский режим, регистрация, роли, почта, биллинг, контент-модуль, React-фронтенд шаблона.
3. Kafka и рассылка почты: модули шаблона остаются в коде, но выключены настройками `MESSAGING_ENABLED`, `KAFKA_PRODUCER_ENABLED`, `KAFKA_CONSUMER_ENABLED`, `MAIL_ENABLED`. Вырезать их код не стоит труда.
4. Медицинские выводы, оценки состояния, рекомендации. Сервис отдаёт числа.
5. Хранение чужих аккаунтов и любой публичный доступ к данным.

## Переход с Python-моста

1. Новый сервис разворачивается в отдельный namespace и синкает тот же аккаунт. На время перехода оба логинятся, и это ровно тот случай, когда ротация токена может мешать. Поэтому Python-мост на время перехода ставится на паузу: CronJob `suspend: true`, деплоймент MCP в ноль реплик.
2. История заливается в Postgres синком нового сервиса с поднятым потолком времени на тип, а не переносом SQLite. Так проверяется весь путь целиком.
3. Сверка за неделю по пункту 5 раздела про тесты.
4. После сверки удаляются `mi-fitness` namespace, PVC и образ `mi-fitness-bridge`.

## Риски

1. Xiaomi меняет закрытые эндпоинты без предупреждения. Смягчение: отдельные метрики на ошибки подписи и расшифровки, честный статус в `sync_runs`.
2. Данных раньше середины июля 2026 в облаке нет, проверено запросом с 1 июня. Глубина истории ограничена сервером, а не клиентом.
3. Двухфакторное подтверждение аккаунта сломает логин: в ответе не будет обязательных полей. Обработка: понятная ошибка `auth`, без попытки автоматизировать подтверждение.
4. Перенос правил нормализации на глаз даст тихо неверные данные о здоровье. Смягчение: золотые векторы, синтетические фикстуры и обязательная сверка с Python-мостом до его удаления.
